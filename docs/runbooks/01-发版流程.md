# 01 — 发版 runbook：从 bump 到三个消费方都升上去

| 项 | 值 |
|---|---|
| **标题** | `openroboto-protocol` 的发版流程（含破坏性变更 / major 的走法与逐步回滚） |
| **日期** | 2026-08-19 |
| **状态** | 草稿（步骤已按仓内现有 workflow 核对；**首次发布尚未发生**，§1 的前置未完成前整份 runbook 跑不通） |
| **来源** | ① 可执行代码：本仓 `.github/workflows/release.yml`（tag 触发 · `pypi` environment · trusted publishing）、`.github/workflows/ci.yml`（`workflow_call` 门槛）、`AGENTS.md` §1② ②本机实测（2026-08-19，见 §2 步骤 1 与 §4）③ `docs/plans/01-解开发布死结.md` ④ `openroboto-backend/docs/specs/08-worker接入协议包说明.md` |
| **适用范围** | `openroboto-protocol` 的每一次版本发布，以及随后 `openroboto-backend` / `openroboto-cli` / 评测方 worker 的升级。**不含**首次发布的前置配置 —— 那在 `docs/plans/01-解开发布死结.md` §5 |
| **关联** | `docs/plans/01-解开发布死结.md` · `AGENTS.md` §1②③ · spec §5（种子派生改了 = 历史评测不可复现）· `openroboto-evaluation/SCOPE.md` |

> **一句话**：`git tag` 是唯一的发布动作。本地不许 `uv publish`。
> **发出去的版本号收不回来** —— PyPI 不允许重传同一个版本，删了也不能再用。
> 所以本文里所有的「验证」都排在 tag 之前，`pypi` environment 的人工审批是最后一道。

---

## 1. 每次发版前，先确认这些是真的

| 检查 | 怎么确认 | 不满足怎么办 |
|---|---|---|
| PyPI 项目 + trusted publisher 已配 | `curl -o /dev/null -w '%{http_code}' https://pypi.org/pypi/openroboto-protocol/json` → 200 | **首发前必须先做**，清单见 plans/01 §5。2026-08-19 实测这里还是 404 |
| `pypi` environment 有 required reviewers | GitHub → Settings → Environments → `pypi` | 补上。没有审批人 = 一个手滑的 tag 直接进 PyPI |
| main 的 CI 全绿 | GitHub Actions | 先修，别用 tag 去试 |
| 版本号已经在**改动那个 PR** 里 bump 过 | `git log -p pyproject.toml` | 见 §2 步骤 1 —— 补 bump 要另开一个 PR，不要直接推 main |

## 2. 常规发版（patch / minor）

### 步骤 1 — 在改动的同一个 PR 里 bump 版本

```bash
uv version --bump patch     # 或 minor。major 不走这里，看 §5
```

**为什么必须和改动同一个 PR**（`AGENTS.md` §1②）：只有写这次改动的人知道它算 patch 还是
minor；留给「发版的人」事后补，等于让一个没看过 diff 的人做这个判断。

实测（2026-08-19，uv 0.10.11）：`uv version --bump minor` 退出码 **0**，
它会**同时**改三样东西 —— `pyproject.toml` 的 `version`、`uv.lock` 里本包自己那条
（`version = "1.1.0"`），以及本地 `.venv`。

⚠️ **`uv.lock` 必须一起提交。** 只改 pyproject 不更新 lock，实测
`uv lock --check` 退出码 **1**（`The lockfile at uv.lock needs to be updated`）——
CI 每个 job 第一步都是 `uv sync --locked`，会**整套变红**，而报错内容和你这次的改动毫无关系。

### 步骤 2 — PR 合进 main，等 CI 全绿

绿的定义是 `ci.yml` 的三个 job：`golden vectors` · `lint + tests (py3.11 / py3.12)` ·
`build (no publish)`。

> `golden vectors` 红**不是**测试挂了，是有人改写了已经发生在链上的历史。
> 这时候不要「修测试」，停下来说明为什么这段历史需要被改写（`AGENTS.md` §1③）。

### 步骤 3 — 打 tag（唯一的发布动作）

```bash
git checkout main && git pull
git tag v1.0.1 && git push origin v1.0.1
```

tag 必须与 `pyproject.toml` 的 `version` 逐字一致。对不上时 `ci.yml` 的
`Tag matches package version` 会在构建前中止，`release.yml` 的
`Artifact version matches the tag` 还会再比一次产物文件名。

### 步骤 4 — 审批

`release.yml` 先 `uses: ./.github/workflows/ci.yml` 把 PR 上那套门槛原样跑一遍，
然后停在 `pypi` environment 等人。**批之前再看一眼三件事**：

1. tag 名字对不对（`v` 前缀、版本号）；
2. 这个 tag 指向的 commit 是不是你以为的那个（`git rev-parse v1.0.1`）；
3. 这次是不是破坏性变更却按 minor 发了（对照 §5 的判据）。

批下去之后 `uv publish --trusted-publishing always` 上传。**这一步之后没有撤销。**

### 步骤 5 — 验证「装得上」，不是「CI 绿了」

```bash
uv run --isolated --no-project --with "openroboto-protocol==1.0.1" \
    python -c "import openroboto_protocol.seed, openroboto_protocol.status; print('ok')"
```

再确认零依赖承诺在 PyPI 上仍然成立（`build` job 已经查过 wheel 的 METADATA，这里查的是
真的从索引装下来那一份）：装完 `pip list` 里除了本包不该多出任何东西
（除非你显式装了 `[schemas]`）。

### 步骤 6 — 推给消费方

| 消费方 | 谁做 | 做什么 | 验证 |
|---|---|---|---|
| `openroboto-cli` | 我们 | 改 `pyproject.toml` 的 `==`，`uv lock`，PR | `protocol-guards.yml` 绿 + `uv sync --locked` |
| `openroboto-backend` | 我们 | 同上；`[schemas]` extra 不要漏 | CI 绿 + 部署后 ingest 无 `ingest:protocol-missing` 告警 |
| 评测方 worker | **对方** | 我们只发通知，不设截止（`openroboto-evaluation/SCOPE.md`） | 我们这侧的 `test_worker_contract_parity.py` 本地跑一遍 |

> ⚠️ 消费方升级**不是**发版的一部分，是发版之后的独立动作。
> 但 minor 里那条「老数据缺这个键必须有默认值」的承诺，只有在消费方**没有**同步升级时才有意义 ——
> 换句话说，如果某次 minor 需要消费方同时升级才能工作，那它其实是 major。

## 3. 出错了怎么办（按发生的时刻分）

| 出错时刻 | 后果 | 处理 |
|---|---|---|
| bump 写错（该 minor 写成 patch），**PR 还没合** | 无 | 改了重推 |
| tag 打错名字，**workflow 还没跑完 / 还没批** | 无 | `git tag -d v1.0.1 && git push origin :refs/tags/v1.0.1`，重新打。**只要还没上传 PyPI，tag 是可回收的** |
| 门槛红了 | 没发出去 | 修完重打 tag（同一个版本号可以重打，因为 PyPI 上还没有它） |
| trusted publisher 配错（`invalid-publisher`） | 没发出去 | 对照 plans/01 §5 逐字核对 owner / repo / workflow 文件名 / environment 名，改完重跑这个 job |
| **已经上传到 PyPI**，发现内容不对 | 🔴 版本号烧掉了 | 见下 |

### 已经发出去了怎么回滚

**没有回滚，只有往前发。**

1. `pip install`／`uv add` 立刻停止推荐这个版本：在 PyPI 上 **yank** 它
   （项目页 → Manage → 对应版本 → Yank）。yank 的语义要说清楚：
   - 已经**钉死**这个版本的消费方（我们的消费方都是 `==`）**照样能装到**，不会被打断；
   - 新的解析不会再选中它。
   所以 yank 是「别再往里踩」，**不是**「把它从世界上删掉」。
2. **删除**（Delete release）只在极端情况用（例如误传了密钥）。删了之后那个版本号
   **永远不能再用**，而消费方钉的正是它 —— 会把已经装好的环境变成不可重建。
3. 修完之后发下一个 patch，并且**主动通知三个消费方**，包括评测方。

## 4. 一个人第一次照着做时最容易踩的三处

1. **只改 pyproject 不提交 `uv.lock`** → CI 整套红，报错和改动无关（§2 步骤 1，实测 exit 1）。
2. **以为消费方 `pyproject.toml` 里的 `==1.0.0` 在钉版本** —— 只要那个仓有
   `[tool.uv.sources]` 的 path / git 覆盖，`==` 就**不参与解析**。
   实测（uv 0.10.11 与 0.11.18 均如此）：声明 `==1.0.0`、装到 `1.2.0`，退出码 **0**，
   `Protocol version is pinned` 检查照样 `pin ok`。
   **升级消费方时，第一件事是确认那个 `[tool.uv.sources]` 已经删掉了。**
3. **在本地 `uv publish`** → 绕开门槛、绕开审批，PyPI 上出现一个没人能复现是从哪个 commit
   打出来的包，而且那个版本号从此烧掉。`AGENTS.md` §3 明文禁止。

## 5. 破坏性变更（major）——「改一个常量 = 改钱怎么分」

### 5.1 先判断：这是不是在改历史

spec §5：**种子派生改了 = 历史评测不可复现。** 这个包里还有几类同样重的东西：
`model_hash`（模型指纹 → 谁的提交算谁的）· `commitment` 编解码（矿工按 A 编码、后端按 B 解码）·
`constants` 里的 `CHAMPION_MARGIN` / `REQUIRED_ENVS`（换王与准入 → 排放怎么分）。

判据只有一条，不看代码改了多少行：

> **同一份链上输入，新版本算出来的结果和旧版本一样吗？**
> 不一样 → 你在改历史，先回答「为什么这段历史需要被改写」，再谈版本号。
> 一样 → 才轮到 patch / minor / major 的讨论。

`golden vectors` job 是这条判据的可执行形式。它红了就是答案已经出来了。

### 5.2 major 的流程（不是「bump 一下数字」）

| # | 做什么 | 谁 | 不做会怎样 |
|---|---|---|---|
| 1 | 写一份**链上数据迁移方案**：哪些轮次按旧规则、哪些按新规则、切换点是哪个 block / round，历史数据如何标注 | 提出改动的人 | 「什么时候开始按新规则算」没有唯一答案 → 两边各按各的理解算钱 |
| 2 | 走评审（`AGENTS.md` §1②：major 需要评审） | 团队 | —— |
| 3 | **先通知，后发布**：给三个消费方，特别是评测方（他们在自己的 GPU 机器上，升级由他们排期） | 我们 | 对方在毫不知情的情况下被换掉规则 |
| 4 | 给一个**迁移窗口**：旧 major 至少还能收到 patch，直到三个消费方都升上去；不设「到期强制」 | 我们 | 见 `SCOPE.md`：我们不替对方决定接入时间 |
| 5 | 发 `2.0.0`。**不要**把破坏性变更塞进 1.x 的 patch/minor —— 消费方钉的是精确版本，它们不会自动升级，但**任何一个新接入方**会装到与已有系统行为不同的代码 | 我们 | 新老消费方对同一份链上数据算出两个结果，而且没有任何一处报错 |
| 6 | 切换点到来时，backend 按轮次门控（round-gated）切规则，而不是靠「大家都升级了」 | backend | 升级时刻 ≠ 规则生效时刻，两者混在一起就没法复现任何一轮 |

### 5.3 明确不做的两件事

- **不原地改 1.x**。哪怕只是「修正一个明显写错的常量」—— 那个「错」的常量已经决定过
  一批矿工的收益，改它就是改历史（§5.1）。
- **不用破坏性变更逼消费方升级**。评测方不升级的成本落在矿工身上，不在我们身上。

---

## 6. 这份 runbook 什么时候会过期

- 首次发布完成后：§1 第一行的 404 变 200，把「首发前必须先做」那条改掉；
- `release.yml` 若改了 environment 名或文件名：PyPI 上那条 trusted publisher 记录要**同时**改，
  否则下一次发布红在 OIDC 交换；
- uv 若修掉了「`[tool.uv.sources]` 覆盖时丢弃 `==` 约束」这个行为：§4 第 2 条与
  plans/01 的 F11 / F12 要重测（它们记的是 uv 0.10.11 / 0.11.18 的实测结果，不是承诺）。
