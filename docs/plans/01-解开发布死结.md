## 1. 今天的事实（2026-08-19 实测）

| # | 事实 | 命令 | 结果 |
|---|---|---|---|
| F1 | 协议包在 GitHub public，**可匿名读** | `git ls-remote https://github.com/openroboto-ai/openroboto-protocol.git` | exit **0**，`HEAD = 4836b4ee…`、`refs/heads/main` |
| F2 | **一个 tag 都没有** | 同上（输出里没有 `refs/tags/*`） | 无 tag |
| F3 | PyPI 上**两个名字都还没被注册** | `curl -o /dev/null -w '%{http_code}' https://pypi.org/pypi/openroboto-protocol/json` | **404**（`openroboto` 同样 404） |
| F4 | git 依赖**今天真的能装** | 见 §3.1 | `uv add` exit **0**，装到 `openroboto-protocol==1.0.0 (from git+…@4836b4ee)` |
| F5 | git 依赖能锁 | `uv lock --check` | exit **0**，lock 里记的是 `source = { git = "…#4836b4ee…" }`（精确 SHA） |
| F6 | 但**按 tag 钉现在钉不了** | `uv add "openroboto-protocol[schemas]==1.0.0" "git+https://…" --tag v1.0.0` | exit **2**，`fatal: couldn't find remote ref refs/tags/v1.0.0`（F2 的直接后果） |
| F7 | git 依赖要求构建环境里**有 git 二进制** | 剥掉 PATH 里的 git 后 `uv sync --frozen --no-cache` | exit **1**，`Git executable not found` |
| F8 | 而 backend 的基础镜像**没有 git** | `docker run --rm python:3.12-slim sh -c "command -v git \|\| echo NO_GIT"` | `NO_GIT`（`Dockerfile:8` 就是 `FROM python:3.12-slim`） |
| F9 | backend CI 的 pin 检查**不认** `uv add` 默认写出来的 git 依赖 | 把 CI 里那段 python 原样跑在探针工程上 | exit **1**，`openroboto-protocol must be pinned to an exact version` |
| F10 | 改成「`==` 版本 + `[tool.uv.sources]` 钉 rev」就能过 | 同上 | exit **0**，`pin ok (1 requirements scanned)` |
| F11 | 🔴 **但那个 `==` 是装饰品** | 声明 `openroboto-protocol==1.0.1` + `[tool.uv.sources]` 指向 git rev（该 rev 上是 1.0.0） | `uv lock` / `uv sync` exit **0**，装的是 **1.0.0**，无任何告警。uv 0.10.11 与 0.11.18 **都是**这样 |
| F12 | 🔴 path 源同样丢弃 `==` —— **这正是 `openroboto-cli` 今天的状态** | 声明 `==1.0.0` + `[tool.uv.sources]` 指向一份版本为 1.2.0 的本地包 | exit **0**，装的是 **1.2.0**，pin 检查照样 `pin ok` |

**F11 / F12 的含义**：只要 `[tool.uv.sources]` 里有 path 或 git 覆盖，`dependencies` 里那个
`==1.0.0` 就**不参与解析**（lockfile 的 `requires-dist` 里连 specifier 字段都没有）。
两个仓的 `Protocol version is pinned` 检查在这种形态下是**绿的、且没有意义的** ——
真正决定装到哪份代码的是 sources 里的 `rev` / `path`。

> 所以「消费方钉死精确版本」这条纪律（`AGENTS.md` §1②）**只有在依赖来自 PyPI 时才真的成立**。
> 覆盖存在时，等价的钉法是钉 **rev（40 位 SHA）**，不是钉版本号。

## 2. 三个解锁条件，今天成立几个

`openroboto-backend/pyproject.toml` 写的三选一，逐条裁定：

### ① 协议包发到私有 index / GitHub，再钉死精确版本 —— **成立一半**

写那段注释时的前提是「协议包仓库当前零 commit、无 remote」，**这句今天已经过期**：
仓库有 2 个 commit、有 public remote、匿名可读（F1）。所以：

- **GitHub 那一半：今天就成立**，git 依赖真的能装能锁（F4 / F5）。代价见 §3。
- **index（PyPI）那一半：不成立**，名字还没注册（F3），CI 里也还没有 publish 那一步。

这是三条里唯一**只差人工动作、不需要改仓库布局**的一条，最短路径走它。

### ② 两个仓收进同一个 uv workspace —— **不成立，且已被后来的决定作废**

两个仓已经是 GitHub 上两个**独立**仓（且可见性不同：protocol public / backend private）。
收进一个 workspace 等于回退仓库拆分这个决定本身，而拆分的理由（`rebuild/README.md`
「边界的三条判据」第 2 条：持有密钥的必须 private）没有变。
**这条不要再评估了，它只会以「本地能跑、CI 和 Docker 都不行」的形式复活。**

### ③ CI / Docker 改成多仓 checkout + 扩大构建上下文 —— **不成立，且最贵**

- CI 侧：`actions/checkout` 加一次 `repository:` 就能拉 public 的 protocol，技术上可行；
- Docker 侧：`Dockerfile` 的 `COPY ./pyproject.toml ./uv.lock ./app /app/` 全部相对本仓，
  要么把构建上下文抬到 `rebuild/` 这一层（把 backend 之外的东西一起塞进上下文），
  要么在镜像里装 git 再拉源码（F7 / F8：得多一层 `apt-get install git`）。

两条都比「装一个 wheel」贵，且都把「装的是哪一份代码」重新变成一个跟目录布局有关的问题。
**只在 ① 被卡死超过一周时才考虑，且优先考虑 §3 的 git 依赖形态而不是这条。**

## 3. 中间形态：能不能先用 git 依赖

**能，但只对 `openroboto-backend` 有意义，而且要按下面这一种写法写。**

### 3.1 实测记录

```bash
# 探针工程 /tmp/orb-gitdep-1，uv 0.10.11
uv init --name gitdep-probe --python 3.12
uv add "openroboto-protocol @ git+https://github.com/openroboto-ai/openroboto-protocol"
#   Updated https://github.com/openroboto-ai/openroboto-protocol (4836b4ee…)
#   Built  openroboto-protocol @ git+https://…@4836b4ee…
# + openroboto-protocol==1.0.0                                     → exit 0
uv lock --check                                                    # → exit 0
```

`uv add` 这条命令**自己**把 pyproject 写成了这样（注意它没写版本号）：

```toml
dependencies = ["openroboto-protocol"]

[tool.uv.sources]
openroboto-protocol = { git = "https://github.com/openroboto-ai/openroboto-protocol" }
```

这份形态**过不了** backend CI 的 pin 检查（F9，exit 1），而且没钉任何 ref ——
main 一动，下次解析就换代码。**要用就必须手写成下面这一种**：

```toml
dependencies = ["openroboto-protocol[schemas]==1.0.0"]

[tool.uv.sources]
# ⚠️ 钉的是 rev，不是上面那个 ==1.0.0：有 sources 覆盖时 uv 会丢弃版本约束（实测）。
# tag 现在不存在（远端零 tag），所以只能钉 40 位 SHA。
openroboto-protocol = { git = "https://github.com/openroboto-ai/openroboto-protocol", rev = "4836b4ee8c27177eb9acd1a21bdc3344fabbd41a" }
```

实测：`uv lock` exit **0** · `uv sync` exit **0**（连带装上 pydantic 2.13.4）·
pin 检查 exit **0** · `import openroboto_protocol.schemas / .seed` exit **0**。

### 3.2 和 PyPI 比，差在哪

| 维度 | PyPI wheel | git 依赖（rev 钉死） |
|---|---|---|
| `uv lock` / `uv sync` | ✅ | ✅ 实测 exit 0，lock 里记精确 SHA，可复现 |
| CI（GitHub Actions，ubuntu-latest） | ✅ | ✅ runner 自带 git，public 仓匿名可读（F1） |
| **Docker 构建** | ✅ 只要能出网 | ❌ **要改 Dockerfile**：`python:3.12-slim` 没有 git（F8），不装就 `Git executable not found`（F7）。多一层 apt、多一次全历史 clone |
| backend CI `Protocol version is pinned` | ✅ 真的在钉 | ⚠️ 形式上过（F10），但 `==` 无效（F11）—— 真正的钉在 `rev` |
| backend CI `No vendored protocol copy` | ✅ | ✅ 与依赖形态无关 |
| 矿工侧 `pip install openroboto` | ✅ | ❌ **不能用**（见下） |
| 评测方 GPU 机器 | ✅ `pip install` 就完事 | ❌ 要求对方机器有 git 且能访问 GitHub |
| 装的是哪份代码，可否被第三方核对 | ✅ 版本号 + PyPI 上的哈希 | ⚠️ 只有 SHA，且 `pyproject.toml` 上那个版本号会撒谎（F11） |

**cli 不能走 git 依赖**：`openroboto-cli` 自己要以 `openroboto` 的名字发到 PyPI，
而 PyPI **拒绝** metadata 里带直接 URL 依赖（PEP 508 direct reference）的分发包 ——
带 git 依赖的 cli 上传会被拒。**（这一条是已知的 PyPI 政策，本次没有实测 —— 实测它需要真的
上传一次；等真发 cli 时会当场知道。）** 无论如何 cli 面向矿工，要求每台矿工机器装 git、
拉 GitHub，本身也不可接受。

### 3.3 结论

git 依赖是**给 backend 的临时解，不是路径的一部分**。

- 只在「PyPI 那步被账号/权限卡住，而 ingest 还在生产上一条提交都入不了队」时启用；
- 启用时 Dockerfile 要加 git，且**这层改动在切到 PyPI 时要删掉**，别留着；
- 启用要在 backend 的依赖表上留一行注释写明「这是临时形态，rev 才是钉子」。

**如果 PyPI 那步不会被卡住，就跳过这一形态直接发包** —— 每多一个中间形态，就多一次
「我们以为装的是 1.0.0，其实是别的」（F11 是这句话的可执行证据）。

## 4. 最短路径：五步，每步的前置条件

> 步骤之间是**严格串行**的，每一步的验证不过就不进下一步。
> 整条路径上唯一需要「人做决定」的是 Step 0。

### Step 0 — 注册 PyPI 项目 + 配 trusted publisher（人工，唯一的阻塞点）

- **前置**：`openroboto-ai` 组织有一个 PyPI 账号并开了 2FA；名字 `openroboto-protocol` 与
  `openroboto` 都还空着（F3，2026-08-19 实测）。
- **做什么**：见 §5 的逐项清单（具体填什么、填错的后果）。
- **验证**：没有「空跑」这个选项 —— `release.yml` 只在 `v*` tag 上触发，而 tag 一推就一路走到
  publish。真正的安全网是它的 `environment: pypi` 人工审批：配错时
  `uv publish --trusted-publishing always` 会**当场红在那一步**（`always` 就是为此选的，
  `automatic` 会静默退回去找 token，错误变成一条看不懂的 401）。
  审批之前 tag 已经打上、版本号已经写进 `pyproject.toml`，但**包还没上传**，
  所以配错的代价只是重跑，不是烧掉一个版本号。
- **卡住怎么办**：走 §3 的 git 依赖临时形态，先解 ingest 的血；**不要**为此改仓库布局（条件 ②③）。

### Step 1 — protocol 发 1.0.0

- **前置**：Step 0 完成；本仓 CI 三个 job 全绿；流 A 的 `release.yml` 已并（`ci.yml` 已经改成
  `workflow_call`，tag 触发挪到 release 那边 —— 门槛只有一份定义）。
- **做什么**：照 `docs/runbooks/01-发版流程.md` §2 走。
- **验证**（不是看 CI 绿，是看装得上）：
  ```bash
  uv run --isolated --no-project --with "openroboto-protocol==1.0.0" \
      python -c "import openroboto_protocol.seed, openroboto_protocol.status; print('ok')"
  ```
  以及 `curl -o /dev/null -w '%{http_code}' https://pypi.org/pypi/openroboto-protocol/json` → **200**。
- **回滚**：见 runbook §4。**发出去的版本号不能收回**，只能 yank + 发下一个。

### Step 2 — cli 切到 PyPI（最简单的一个，先拿它验证发布是真的可用）

- **前置**：Step 1 验证通过。
- **做什么**：删掉 `openroboto-cli/pyproject.toml` 的 `[tool.uv.sources]` 那一段
  （它自己的注释已经写了「发布前这一段要删掉」），`uv lock`，提交 lock。
  依赖行 `openroboto-protocol==1.0.0` 一个字不用改。
- **验证**：`uv sync --locked` 通过；`protocol-guards.yml` 绿 —— 而且这次 `Protocol version is
  pinned` 是**真的**在钉（F12 说明它在删掉 sources 之前是装饰品）。
- **回滚**：把 `[tool.uv.sources]` 加回去，`uv lock`。零风险，纯本地。

### Step 3 — backend 把依赖加回去

- **前置**：Step 1 验证通过（Step 2 不是它的前置，但先做 Step 2 能便宜地证明发布可用）。
- **做什么**：把 `openroboto-backend/pyproject.toml` 里那段注释换成真的依赖
  `openroboto-protocol[schemas]==1.0.0`（`[schemas]` 是必须的：backend 用
  `openroboto_protocol.schemas`），`uv lock`，提交 lock。
  **Dockerfile 不用动** —— PyPI wheel 走 https，不需要 git（对照 F7 / F8：这正是不走 git 依赖的原因）。
- **验证**：
  - CI 的 `Protocol version is pinned` 从「扫到 0 条」变成真的扫到一条并通过；
  - `uv sync --locked` 在 CI 与 Docker 构建里都过；
  - **ingest 不再触发 `alert(key="ingest:protocol-missing")`** —— 这是这一步的业务验收，
    不是 CI 绿。停在 `seed_failed` / `retrying` 的提交应当重试成功。
- **回滚**：注释掉依赖行 + `uv lock`。行为退回今天（ingest 重新 lazy import 失败 → 可重试 + 告警），
  **不会丢数据**。

### Step 4 — 删掉 3 处副本（死结真正解开的那一刻）

- **前置**：Step 3 已上生产且 ingest 恢复；并且——**这条容易被跳过**——
  三处防漂测试在协议包**真的装上**的环境里全绿（不是 skip）。
  「能装上」不等于「装上的内容 == 副本内容」，只有测试从 skip 变 pass 才证明这一点。
- **不是 3 处，是 5 处**（§7：文档里有三种说法，以代码为准。2026-08-19 逐个文件核对）：

  | # | 副本 | 抄的是什么 | 谁守着 |
  |---|---|---|---|
  | 1 | `app/domain/worker_reports.py`（整个模块） | `schemas` 的常量 + `status` 词表 | `tests/domain/test_worker_reports.py` |
  | 2 | `app/domain/reasons.py:44` 起 | `schemas.ReasonCode` | `tests/api/routes/test_queue_submissions.py` |
  | 3 | `app/api/envelope.py`（复制段） | `schemas` 的「响应信封」一节 | `tests/api/test_envelope_parity.py` |
  | 4 | `app/services/legacy_views.py:90` 起 | `constants.LIBERO_TASK_SUITES` | `tests/api/routes/test_legacy.py` |
  | 5 | `tests/api/routes/test_legacy.py:180` 起 | `status.ALL_STATUSES` | 无（**测试自己就是副本**） |

  第 5 处最容易漏：它住在测试文件里，任何「只扫 `app/`」的检查都看不见它。
- **做什么**：删副本 → 改成 `from openroboto_protocol import …` → 防漂测试从「逐项比对两份」
  改成「直接断言协议包的值」，**不要连测试一起删**：断言换了源头，仍然是那几条词表的唯一守卫。
- **验证**：`No vendored protocol copy` 这条检查此时才第一次有东西可抓（它今天只防「再开一个新的
  `protocol/` 目录」）；全套测试绿；`/api` 的响应词表逐字不变。
- **回滚**：git revert 单个提交。副本删除是纯代码变更，不涉及数据。

### Step 5 — 通知评测方（**不是**前置，也没有截止日期）

见 §6。这一步可以和 Step 2 / 3 并行，**但绝不能挡住它们** ——
「先发包，他们什么时候接都行」是 `openroboto-evaluation/SCOPE.md` 定的边界。

## 5. 只有人能做的（Step 0 的清单）

1. **决定 PyPI 账号归属**：用组织账号还是个人账号发 `openroboto-protocol`。
   个人账号发出去之后转移所有权是有摩擦的，**发第一版之前就要定**。
2. **PyPI → Your projects → Publishing → Add a new pending publisher**
   （项目还不存在时用 pending publisher，不需要先手工上传一次）：
   - Owner: `openroboto-ai`
   - Repository name: `openroboto-protocol`
   - Workflow name: `release.yml`（**必须和仓库里那个文件名逐字一致**，改名 = 发布当场
     `invalid-publisher`）
   - Environment name: **`pypi`** —— `release.yml` 的 publish job 上写死了
     `environment: name: pypi`。两边不一致同样是 `invalid-publisher`。
3. **GitHub → Settings → Environments → `pypi` → 加 required reviewers**。
   这个 environment 今天在仓库里还不存在（`release.yml` 引用它，GitHub 会在第一次用到时
   自动建一个**没有审批人**的）。不配审批人，那道「上传不可撤销、版本号不可重用」的闸门
   就是敞开的。
4. **同一套再做一遍给 `openroboto-cli`**（PyPI 项目名是 `openroboto`，仓库名是
   `openroboto-cli` —— 两者不同，别填串）。
5. **不要创建 API token**。trusted publisher 的全部意义就是不存在一个能被泄露的长期凭据；
   `release.yml` 的 `permissions: id-token: write` 已经在位，不需要任何 secret。

## 6. 评测方那一侧（`openroboto-evaluation`）

**这个仓不是我们负责的**（它的 `SCOPE.md` 第一行就这么写），跑在评测方的 GPU 机器上。
它是协议包的第三个消费方，但它的接入时间**不由我们决定**。

### 我们能做什么

| 能做 | 具体是什么 |
|---|---|
| 发包 | 让 `pip install openroboto-protocol==1.0.0` 在他们的机器上能成功。主包 `dependencies = []`，装它**不往评测环境塞任何第三方包**，worker 那条「通信层零第三方依赖」的原则不受影响 |
| 通知 | 把 `openroboto-backend/docs/specs/08-worker接入协议包说明.md` 发过去 —— 那是写给他们维护者的说明，不是要求 |
| 给迁移窗口 | 破坏性变更时旧行为至少保留一个完整的迁移窗口（runbook §5 定义），并且**先通知再发**，不是发完再通知 |
| 单方面对账 | 见下 |

### 不能做什么

- 不替对方决定接入时间，也不设截止日期；
- 不给对方提 PR 改 `libero_eval/` 的评测执行逻辑；
- 不把「对方还没接」写成阻塞项挂在我们的路径上（§4 Step 5 是并行的）；
- 不做破坏性变更来「逼」对方升级 —— 对方不升级的成本落在矿工身上，不在我们身上。

### 今天靠什么保证两边不漂

`openroboto-backend/tests/test_worker_contract_parity.py` 在**单方面对账**：
断言一律从对方代码里取（读 `_PROGRESS_STAGE_MAP`、调对方的 `build_score_payload()`、
调对方的 `remote_score_matches()`），不自己抄一份字面量 —— 抄一份就等于造第五套词表。
它按「今天的实际状态」写断言，**包括两处已知分歧**；分歧被消除时它会红，那是好事。

⚠️ **这套对账有一个天花板，必须写下来**：它靠 `sys.path` 挂同级目录找
`openroboto-evaluation`，而 backend 的 CI **只 checkout 本仓**。
也就是说**这条对账在 CI 里是 skip 的，只在本地有兄弟目录时才真的跑**。
今天两边不漂，靠的是「有人在本地跑过全套测试」，不是一条会变红的流水线。
发包之后这条天花板不会自动消失 —— 词表那一半会因为两边 import 同一个包而消失，
**端点路径那一半不会**（那仍然是字符串）。要真正消除，需要 backend CI 额外
checkout public 的 `openroboto-evaluation`，那是发包之后单独的一件事。
