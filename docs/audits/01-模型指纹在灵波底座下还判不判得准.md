## 1. 指纹拿什么当输入

`model_hash.py:117-135`，读代码不是读文档：

```
取 type == "file" 且带 lfs 的条目 → sha = lfs.sha256 or lfs.oid
→ 全部 sha 排序 → "\n" join → sha256 → 小写 hex
空集合返回空串（哨兵，backend 判 reject_reason=model_hash_empty）
```

四条推论，后面每一节都建立在它们上面：

| 参与指纹 | 不参与指纹 |
|---|---|
| 每个 LFS 文件的内容 sha256 | **文件路径**（换 repo 名、换 `global_step_50000` 目录名、整棵树挪位置都不变） |
| 文件的**个数**与重复次数（不去重） | **顺序**（先排序，重传洗不掉） |
| | **非 LFS 文件**（`config.json` / `model.safetensors.index.json` 改一行不改指纹） |

**聚合方式是「整体一次 sha256」，不是逐分片比对。** 这一条是第 2 节的全部。

**`lfs.oid` 确实就是内容 sha256（实测，不是推断）**：下载
`lingbot-vla-v2-6b-robotwin` 的 `assets/lingbot_vla2_framework.png`（234 893 B），
本地 `shasum -a 256` = `5e7fccb5…13d7`，与 tree API 给的 `lfs.oid` 逐字符相同。
两个仓都已经是 Xet 存储（tree 响应里带 `xetHash` 字段），**`lfs.oid` 照给** ——
这顺带消掉了上一版审计里「Xet 之后还有没有 oid」那条不确定项的一半（见 §5.1）。

## 2. 假阳性（误判抄袭）：没有变差，且结构上不可能变差

命中即 `mark_rejected(plagiarism_detected)` 写终态，这是最贵的方向。担心的是：
灵波 25.5 GB / 6 分片，矿工只动一部分参数 → 两个矿工的分片里会不会有大量逐字节相同的部分。

**实测（今天唯一存在的一对「微调前 / 微调后」真实权重）：**

| | `lingbot-vla-v2-6b`（底座） | `lingbot-vla-v2-6b-robotwin`（官方后训练） |
|---|---|---|
| revision | `11c703bf…53d7` | `0451855729ec…3afe` |
| LFS 文件数 | 12 | 8 |
| 6 个分片 oid 相同的个数 | — | **0 / 6** |
| 两仓共享的 LFS oid | — | **只有 1 个：`tokenizer.json`（`aeb13307…dae4`），不是权重** |
| 指纹 | `78782ad3…0d22` | `168ccdcd…02ce` |

**但真正的答案不在这张表里，在聚合方式上。** 就算某天真出现两个矿工共享 5 个分片
（比如都设了 `freeze_vision_encoder: true`，冻住的那部分落在同几个分片里），
**也不会撞指纹** —— 指纹是对**整张排序后的 oid 列表**做一次 sha256，
12 个里对上 11 个跟对上 0 个的结果一样：一个毫不相干的值。
**算法里没有任何一处做逐分片匹配，也没有任何「相似度」概念。**
碰撞的充要条件仍然是：**每一个 LFS 文件都逐字节相同**。

所以分片多、模型大、只训一部分 —— 这三件事**一件都不影响假阳性**。
换底座在这个方向上**没有变差**。
钉在 `tests/test_model_golden_vectors.py::test_fine_tuning_leaves_no_shard_byte_identical`。

**一条本来会新增、但被准入顺序挡掉的假阳性**（值得记下来，因为它依赖别人不改顺序）：
灵波底座的非权重 LFS 文件是**所有矿工共享**的（`tokenizer.json` 11 MB 必进 LFS）。
如果一个仓里**只有**这些共享文件而没有权重（`save_hf_weights` 的异步转换失败就是这个形状），
两个这样的仓会算出**同一个指纹** —— 而 π0.5 时代同样的仓算出的是**空串**（判 `model_hash_empty`，
一条自己的拒绝，不是抄袭）。
今天这条打不出来，因为 `admission.py` 的**第 4 步 `adapter.judge_tree()` 在第 6 步指纹之前**，
缺分片先被 `MISSING_WEIGHTS` 拒掉。
🔴 **谁要调换这两步的顺序，先回来看这一段。**

## 3. 假阴性（漏判抄袭）：变差了，两条入口

### 3.1 非权重文件进了指纹（上一版审计已发现，本次补上实测对照）

π0.5 三份真实提交的 LFS 集合**就是权重**（uid 221 一个 `model.safetensors`；
uid 181 / uid 130 是 4 个 / 8 个 orbax `params/…` 分片，没有第二种东西），
所以「指纹 = 这份权重」当时事实上成立。灵波不成立：底座 12 个 LFS 里 6 个不是权重
（3 张 README 图 + 冻结的 `depth/model.pt` + `dino_video/teacher_step_10000.pth` + `tokenizer.json`）。

**新证据**：官方后训练产物里 `depth/` 和 `dino_video/` **没有了**（矿工的导出大概率也没有），
但那张 `assets/lingbot_vla2_framework.png` 还在 —— **而且和底座那张不是同一个文件**
（234 893 B / `5e7fccb5…` vs 1 178 043 B / `1dbbf057…`）。
非权重 LFS 文件**会独立于权重自己变**，这不是假设，是厂商自己两个仓之间已经发生过的事。

后果：抄袭者复制别人的 6 个分片、顺手换掉一张 README 图，指纹就变了。
钉在 `test_lingbot_fingerprint_is_not_only_the_weights`。

### 3.2 🔴 重新导出会换分片（本次新发现，比 3.1 更难防）

两个 revision 的 `model.safetensors.index.json` 实测：

- 张量名集合**完全相同**（1708 个，`set(base) == set(robotwin)`）；
- `metadata.total_size` **一模一样**：`25 503 630 044` 字节；
- 但 **1708 个张量里有 1446 个被分到了不同的分片文件**，6 个分片的长度也两两不同
  （底座 shard1 = 4 987 151 072 B，后训练 shard1 = 4 947 507 248 B；总长只差 648 B）。

**张量落在哪个分片，是「谁跑的导出」的属性，不是权重的属性。**
于是「同一份权重换个人 / 换个 world size / 换个 transformers 版本重导一次」
就可能得到 6 个全新的 oid → 全新的指纹，而 backend 认不出这是同一个模型。

这条比 3.1 难办的地方在于：**收窄到「只哈希权重文件」也挡不住它** ——
被换掉的正是权重文件本身。真要挡住只能读 safetensors header 按张量算
（就是 ZCY-212 的方向），**本次不建议做**。
钉在 `test_lingbot_shard_bytes_are_export_dependent`。

### 3.3 没变差的那一半（顺带确认）

路径不进指纹，所以**换仓名、改 `global_step_50000`、把整棵树挪出 `checkpoints/…/hf_ckpt/`
都不改指纹** —— 实测把后训练那棵树的所有路径拉平到根，指纹仍是 `168ccdcd…02ce`。
灵波的嵌套目录名里带步数（每个矿工都不一样），这条恰好是换底座之后**更有用**的性质。

## 4. 建议怎么办（🔴 不动指纹算法）

1. **协议包零改动。** 改 `model_hash` 的口径 = 链上每一个历史指纹作废
   （AGENTS.md §1② major + 链上数据迁移），而 §3.1 的收益可以在调用方拿到：
   backend 的 `_check_plagiarism()` 喂给指纹的**条目集合**，从「整棵树」收窄成
   「本期 layout 认的权重文件」。这不需要本包出新函数 —— `extract_lfs_sha256`
   与 `fingerprint_lfs_sha256` 本来就是分开导出的，就是给调用方自己组集合用的。
2. **收窄必须按赛事分派，不能全局改**：同样的收窄用在 π0.5 上会改掉 round 1 已经写进
   `submissions.model_hash` 的值。`(sim, 1)` 继续走 `model_hash_from_hf_tree`，
   `(sim, 2)` 走收窄版 —— 正是 `08-24-competition-adapter-dispatch` 那套分派。
3. **§3.2 明确不修，写进赛制文档而不是写进代码**：告诉矿工「提交后不要重导权重」
   拦不住恶意方，但能避免诚实矿工自己踩。真正的解法是张量级指纹（ZCY-212）。
4. **不要动 `admission.py` 第 4 步与第 6 步的先后**（理由见 §2 末尾）。

## 5. 不确定的部分

1. **矿工新建的仓，HF tree API 会不会稳定给出 `lfs.oid`。**
   已确认的一半：这两个仓**已经是 Xet 存储**（响应里有 `xetHash`），`lfs.oid` 照给，
   且 oid 经下载核对确实是内容 sha256。**没确认的一半**：2026 年新建的仓、
   大文件走 `xet` 直传上传的路径，响应形状没有样本可验。
   若某天只有 `xetHash` 没有 `lfs`，指纹会退化成空串 → `model_hash_empty` → **误拒**。
   **要确定需要**：第一个矿工建的灵波仓上链时人工看一眼 tree 响应。
2. **同一条导出流水线重跑一次，分片切分是否稳定。**
   §3.2 证明的是「两次导出切法不同」，但这两次**很可能是两条不同的流水线**
   （底座是厂商的 HF 发布，后训练那份是训练脚本的 `save_hf_weights` 写的）。
   「同一个脚本、同样的 world size、重跑一次是否逐字节相同」**没有样本，无法判定**。
   **要确定需要**：拿同一个 dcp checkpoint 跑两次 HF 转换，比 6 个 oid。
   ⚠️ 注意：即使答案是「稳定」，§3.2 的风险也只降不消 ——
   矿工之间的 world size / 库版本本来就不一样。
3. **矿工的导出里还会不会出现别的非权重 LFS 文件。**
   已知官方后训练产物只剩 `png` + `tokenizer.json`；矿工会不会加 wandb 产物、
   视频、eval 结果，**没有真实矿工提交可验证**。方向不变，量不确定。
4. **两个矿工都原样上传官方权重会撞指纹。** 那确实是「同一份权重」，判重复没错；
   业务上想说的是「这两个都没训练」，是另一件事。π0.5 时代同样存在，
   **本次不处理**，记在这里免得被当成换底座引入的新问题。
